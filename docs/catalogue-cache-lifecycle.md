# 官包元数据缓存与断点备份

## 本次故障

小米两次失败均发生在采集后导出加密快照：`ValueError: Oversize snapshot`。
页面正文与正式机型/版本断点混存，正文缓存无总量和条数淘汰，导出又将它们全部打包。
更严重的是导出失败仍留下上一次成功生成的文件，`always()` 上传步骤把旧文件当新产物上传，产生成功备份的假象，并可能在续跑时覆盖本机较新进度。

## 新的生命周期

- 页面是可重建缓存，机型、版本、控制记录、解析结果是必须保留的断点。只允许按 `v2:<vendor>:page:*` 淘汰页面。
- 每厂商持久页面缓存同时受 **64 MiB、2048 项**限制。启动先清过期项，新增前按最近访问时间淘汰到预算内。
- 新条目按其 freshness TTL 加一天作为 stale revalidation 保留期，上限 30 天。命中不延长正文保留期；ETag/Last-Modified 条件请求仍保留。
- 压缩页内存缓存上限 8 MiB；解析器的原始响应内存缓存上限 16 MiB，均按字节做 LRU。单页响应限制保持 8 MiB。
- 小米任务开始前清理历史积累并在空闲页超过 32 MiB 时压缩本地 SQLite。输出分类条数、字节及物理文件大小前后对比。
- 快照通过 SQLite online backup 获取一致视图；**只在副本中删除所有页面缓存，再 VACUUM**。本机预算内缓存仍保留，完整机型、版本及续跑断点都保留。
- 现有加密快照 256 MiB、解码 SQLite 1 GiB 的保护上限不提高。

## 失败与恢复

- 新采集开始即移除旧上传文件；导出前再移除一次。新文件通过临时文件、成功 seal 和原子 replace 生成。
- 采集未执行时禁止上传旧文件；生成失败时没有可上传的新产物，不伪报备份成功。
- 修改前将本机状态标记 `dirty=true`，成功生成新备份才置回 false。未导出的本机提交优先于远端旧产物，不因备份失败而回滚重抓。
- 首次缓存修复只处理已有本机状态，不先恢复旧远端备份。清理有改动时也标记 dirty，保护已推进的解析结果。
- 新增日志 `metadata_cache_maintenance`、`metadata_cache_budget`、`checkpoint_export` 可核对回收量及缓存不进入快照的结果。
