# 厂商采集与 D1 发布

每厂商一个 `catalogue_<vendor>.yml`：采集元数据、复用页面缓存、解析链接。
任务不持有 Cloudflare 凭据，不访问线上 D1。存在积压时每批最多约 7 分钟，
先上传加密 SQLite 检查点，再自动提交下一批；无积压后按原刷新计划检查新增。
公开日志只含阶段、数量与错误类别。每 30 秒输出心跳。

统一发布入口是 `catalogue_publish.yml`，cron 为 `*/10 * * * *`。
各厂商最新快照中的新增记录会轮流入库，避免小米积压阻塞其他厂商。
GitHub 计划任务可能因排队延后，因此这是 10 分钟计划频率，不是严格延迟承诺。
统一发布任务通过并发组串行化，同一 10 分钟窗口的重复启动会跳过。

采集页面、JSON 检查点、游标、缓存、发布确认点使用域分离的 AES-GCM 加密，
存入 GitHub Actions artifacts。每个入口只保留最新三份快照，不需要 R2；
快照只含元数据，不含固件或镜像。首次切换先只读迁移旧 D1 检查点，
保留所有原记录，不重新抓取已有历史；迁移失败时不会启动新采集器。
恢复时如快照认证失败则停止，避免默默清空队列。90 天过期或密钥轮换前
需另行迁移快照；不要删除最后一份有效快照。

发布确认点以内容哈希去重，未变化的已同步记录不访问 D1。D1 成功后
才确认发布；网络故障导致重放时保留原 public_token、签名和提取状态。
每批最多处理 180 个机型/固件记录，剩余留待下个窗口。
使用现有项目预算：每日预留上限 2,000,000 读行 / 40,000 写行，
按响应 meta 的实际行计量（含索引写入），单批留出结算余量。
完成后释放未使用的预留；异常退出则保守保留全部预留至 UTC 日重置。
触顶只暂停发布，不停止采集，不丢弃待发布记录。访客与其他非此入口
的 D1 请求不在这份项目预算中，因此不能凭十分钟频率保证全账号永不超额。

失败排查：各厂商日志查看发现/解析阶段；统一发布 Summary 查看新增、失败与
D1 实际行数。默认增量续跑，`retry_failed` 重试缺口，`refresh_sources` 重新核对
来源；都不会删除已经保存的任务。元数据迁移不应停用独立的云端镜像提取，
也不修改 Sony 的固件打包下载策略。


## 固定主机与并行槽位

固定主机使用 `FMR_CATALOGUE_STATE_DIR` 指定的共享目录持久保存各厂商 SQLite、发布确认点和备份版本戳。
目录位于 checkout 清理范围之外，权限为专用服务用户所有。正常重启只检查少量 artifact 版本信息；
本机已有最新状态时直接续接，不重读 D1 历史、不重新下载自身刚上传的快照。
本机文件缺失或发现其他执行器更新的备份时才恢复对应的加密快照；损坏或来源不明的本机状态明确报错。
每个厂商写入仍受各自并发组串行保护；共享目录增加恢复锁和版本戳锁，备份通过 SQLite online backup 生成一致快照。
发布侧读取已有 schema，不在厂商状态库里反复初始化或修改基础数据。

`ops/setup_metadata_runner.sh` 按实际 CPU、cgroup 内存和磁盘余量配置至多 4 个采集槽位，另设独立发布槽位。
槽位均使用专用非 root 服务用户；复用已安装的 Runner 二进制，避免逐个联网下载。
采集标签为 `findmyrom-metadata`，发布标签为 `findmyrom-publisher`；
变量 `FMR_PUBLISH_RUNNER` 独立指定发布池，避免发布被采集队列占满。
先核对全部服务在线，再更新路由；不停止正在处理的采集任务，不调整镜像提取或 TG 的运行位置。

旧 D1 到任务侧的整库读取是一次迁移。成功后保留 `FMR_CATALOGUE_MIGRATED=true` 标记，
即使原迁移 artifact 过期，也不会因再次执行 bootstrap 而自动重读旧 D1 状态。
加密快照仍是完整恢复备份；普通采集与发布优先使用本机持久数据库。
发布记录筛选目前仍有本地 SQLite 遍历，不能据此宣称所有本地计算都是常数复杂度。

## 云端镜像队列与暂停发布

链接采集与十分钟统一发布仍在固定主机；`batch_extract.yml` 固定使用
GitHub 托管的 `ubuntu-latest`，不读取采集执行器路由变量。
新发布的完整、静态 HTTPS ZIP 会进入 `pending` 队列；增量 OTA、TGZ、
OZIP、需刷新/设备证明的地址、Sony 分块包及暂停品牌不进入这条提取队列。
入队表示待尝试提取，不代表上游一定支持 Range，也不代表已经获得镜像。

提取运行按固件发布日期优先处理新包，单批最多 100 包、4 个并行，
运行预算 15 分钟，每包仍受 250 MiB Range 下载限制。保留原每六小时计划。
历史误标为 `skipped` 的完整静态 ZIP 可通过手动输入 `repair_skipped=true`
一次补队列；先用 `dry_run=true` 查看数量。修复保留已完成/处理中/失败记录、
尝试次数非零的记录和已有镜像，不重签链接、不删除资源。

仓库变量 `FMR_D1_WRITES_PAUSED=true` 会挡住发布与提取工作流；对应 CLI
也在构造数据库/网络客户端前返回。本地只采链接、只保存检查点的任务继续。
恢复需要解除暂停并明确启用发布/提取入口；不会因日期变化自动解锁。
`FMR_EXTRACTION_ENABLED=true` 是镜像提取的独立开关。

明确允许恢复 D1 后，在已登录 `gh` 的工作目录运行一次
`python3 ops/resume_catalogue.py --apply`：它会配置两个入口、解除统一暂停，
立即触发本地主机发布和云端镜像提取，并包含历史误跳过队列的保护性修复。
不带 `--apply` 仅离线显示计划，不发网络请求。此命令不会在操作电脑上读取
D1 或下载固件，也不会启动三星/华为/荣耀或旧版历史扫描。

快照传输上限仍为 256 MiB，解压后的元数据库上限单独设置为 1 GiB。
写入和恢复使用一致上限，备份时压实空闲页，保留缓存和检查点。
这处理了小米历史快照增长后无法被原 256 MiB 解压上限恢复的问题。
